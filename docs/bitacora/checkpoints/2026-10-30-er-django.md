# Conflictos y riesgos detectados

- Sin colisión física de nombres encontrada entre las 13 tablas actuales y las tablas lógicas planeadas.
- Mantener `AUTH_USER_MODEL=accounts.User` como identidad y FK destino; no crear otro usuario.
- No reutilizar `auth_group`/`auth_permission` para cargos organizacionales. Separar también la Superadministradora de `User.is_superuser`, que otorga el bypass técnico estándar de permisos Django.
- Brecha estructural: `AuthChallenge.user_id` y `contact_id` pueden apuntar a usuarios distintos. El servicio normal asigna ambos correctamente, pero las dos FK no prueban propiedad mutua. Para cerrar, validar filas actuales y agregar una protección PostgreSQL por migración (FK compuesta o trigger revisado), coordinada con el estado de migraciones Django.
- `LoginThrottle` y `AuthAttempt` se conservan separados: el código los usa para alcance de login y alcance de contacto/cuenta/IP. No se observa duplicación funcional que justifique unificarlos.
- Contactos de email se normalizan en el servicio; la unicidad PostgreSQL por `type,value` es sensible a mayúsculas. SQL directo/importación podría eludir la normalización de aplicación; al diseñar futuros caminos de escritura, mantener el servicio como dueño o considerar índice funcional normalizado.

La lista de tablas es del esquema de aplicación que Django introspecta, no incluye catálogos internos `pg_catalog` de PostgreSQL. No se consultaron valores de filas de usuarias; solo conteos agregados. `AuthChallenge` tiene 0 filas, así que no se observó un caso inconsistente, aunque el esquema permite el cruce. Tampoco se encontraron grupos de contactos verificados duplicados al comparar sin distinguir mayúsculas. No se ejecutaron pruebas del producto porque el cambio solicitado es documental y de inspección de solo lectura.
